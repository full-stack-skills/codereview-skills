# OCR 项目规则治理

OCR 规则告诉审查者关注哪些**语义风险**，不是运行 lint、编译或测试的替代品。只有用户要求变更项目审查策略时才修改 `.opencodereview/rule.json`；普通代码审查只读取并说明现有规则。

## 什么时候使用、范围和权限

- 先看当前目标仓库规则、全局规则和显式 `--rule` 参数；按 OCR 当前版本核实实际优先级。不要假设所有版本字段一致。
- 变更项目文件前确认用户意图和现有修改，保留未知字段与人工注释策略。JSON 不支持标准注释；不要为了改一项重写整套文件。
- 规则可能影响 OCR-managed 的模型上下文，也可能改变提交前插件的授权配置摘要。规则变化后旧报告失效；先返回 harness 重新准备，不偷偷复用旧授权。
- 不安装/升级 OCR，不试跑真实模型；`ocr rules check <path>` 是规则匹配探测，不证明审查质量。

## Workflow / 工作流

### Step 1 — 定义可检验规则
将要求改写为对象、路径、风险、反例与排除项。例如“审查订单幂等”优于“检查所有代码质量”。

### Step 2 — 检查优先级和范围
核对现有规则命中顺序，判断替换还是合并默认规则；使用最窄而足够的路径模式，并准备应命中与不应命中的代表文件。

### Step 3 — 修改与验证
修改后验证 JSON 语法，再运行 `ocr rules check`；记录实际命中、规则来源、合并情况及 CLI 版本。若 CLI 不支持该命令，不能凭字符串匹配声称已验证。

### Step 4 — 安全与交付
排除执行不安全命令、泄露凭据或越过用户同意的规则内容；交付 diff、匹配证据和未验证边界。真实 OCR 审查需另行授权。

语法和匹配样例见 [规则样例与陷阱](references/rule-contract.md)。

## 不适用

需要可执行格式/静态门禁时交给 CodeGuard；需要需求验收或强制放行策略时交给 FlowGuard；只想审查一次且不改团队策略时用官方 `open-code-review` / `open-code-review-delegate`。

## Gotchas / 易错点

- 第一条命中规则若替换内置规则，会意外失去系统检查；按实际优先级核对合并。
- `rules check` 证明命中，不证明模型真的发现缺陷。
- 宽泛路径会增加噪声和费用；缩小到业务边界再验证近似路径。
- 规则更改后旧报告的配置摘要不再有效，提交前返回 harness 重新准备。
