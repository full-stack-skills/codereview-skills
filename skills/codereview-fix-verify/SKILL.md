# 审查问题修复与验证

适用“修复这条高风险问题并确认”或“review and fix”。单纯“审查一下”只允许报告，不授权修改。开始前检查用户指定的修复范围、其他未提交改动与当前候选状态。

## 什么时候使用与能力边界

只在用户明确要求修复审查发现时使用；仅要求 review 时交给发现核实，不改代码。需修改核心需求、迁移数据或扩大修复范围时，先展示影响并取得方向。

## Workflow / 工作流

### Step 1 — 核实问题与授权
只接受已核实的问题或用户明确选择的待验证假设；证据不足先交给 `codereview-finding-triage`。审查授权不包含修改、安装依赖、模型外发、提交或推送。

### Step 2 — 复现与修复
先写或更新能重现目标行为的测试，确认它因目标问题失败；无法自动测试时记录手工验证步骤。做最小修复，保护用户已有修改，不改写无关代码或压制规则。

### Step 3 — 验证与重审
运行目标测试和受影响回归，保留命令、退出码与失败。内容变化使原 OCR 报告/插件指纹过期；手动审查重跑同一目标，插件候选提交重新 `prepare` 和 `review`，不能复用旧 `proceed`。

### Step 4 — 逐条交付
对比原问题和新结果，报告“已修复/仍存在/未验证”、新引入风险及未覆盖测试；不自动 commit/push。

检查 [修复回路示例](references/fix-loop.md) 处理部分暂存和模型建议代码。输出的“修复完成”只表示受测行为与当前候选一致，不代表项目最终验收。

## 停止条件

- 用户只请求 review、没有修复授权：停在建议。
- 修复会触及未知数据迁移、外部 API 合约或大量非目标文件：先说明影响并请求方向。
- 测试环境缺失或新审查失败：明确 `UNVERIFIED`，保留改动与失败证据，不宣称闭环。

## Gotchas / 易错点

- 修复只在工作区、未进入暂存区时，插件旧报告仍不能证明新候选已修复。
- 模型建议代码可能破坏其他调用方；先验证类型、异常和并发路径。
- 测试通过不等于重新审查通过，两种证据分别记录。
- 用户要求修复一条发现不意味着授权顺手修改所有同类文件。
