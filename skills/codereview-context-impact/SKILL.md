# 审查上下文与影响分析

目标是让 OCR 或宿主审查者知道“这次修改必须保持什么”，而不是把一段泛化需求塞进提示词。适合跨模块 API、状态机、持久化结构、权限边界或兼容性变更；普通单文件格式修改不必启动。

## 什么时候使用与能力边界

当审查结论依赖“为何修改”和跨文件行为时使用；若只是检查格式、编译或依赖漏洞，转交 CodeGuard。没有正式规格时仍可整理代码中的可观察行为，但不得补造验收标准。

- 输入：用户明确的审查目标、候选差异、相关规格/测试和项目上下文。只读分析；缺少目标时先指出能确定的范围，不猜测需求。
- 输出：可追溯的背景摘要、影响路径、需要审查的行为假设和未知项。没有证据的影响只能标为“待核实”。
- 在 `codereview-plugin` 的提交前流程中，仅分析它提供的**授权后快照**；不要直接读取实时工作区并冒充暂存内容。没有快照时先回到 `codereview` harness。
- 上游 `ocr review --background` / `--background-file` 是手动 OCR 审查的输入接口。提交前插件若无安全的背景注入接口，只向审查者展示摘要；不要绕开插件直接运行 `ocr review`。
- 不调用模型、不安装工具、不外发代码、不修改源文件，也不决定是否提交。读取源码与规格仍受用户披露范围限制。

## Workflow / 工作流

### Step 1 — 固定审查对象
区分工作区、分支范围、单提交、全文件扫描和插件候选快照。记录基线与目标；不同对象不得混用。

### Step 2 — 提取意图
优先看用户当前要求和正式规格，再看设计、任务、测试。旧 README 与注释只能作线索，冲突时说明冲突。

### Step 3 — 定位影响
从改变的入口、公开 API、调用方、数据读写、权限检查、异步/并发边界和测试反向追踪。仓库有 `.codegraph/` 时先用 CodeGraph；没有则用只读搜索。不要为本技能初始化索引。

### Step 4 — 压缩并校验背景
列出需保持的可观察行为和负例，缩成目的、变更边界、三个最重要的不变量、受影响路径、缺失证据。背景必须对应当前候选；对外发模式先展示背景及接收方，不扩大原授权范围。

如需字段样式及典型误用，读取 [背景与影响模板](references/background-contract.md)。

## 交付格式

```text
审查对象：<类型、基线、候选标识>
业务目的：<一句话；出处>
必须保持：<行为 + 出处；最多三项>
影响路径：<入口 → 调用方/数据/外部契约；逐项证据>
重点风险：<可证伪的问题，不作结论>
未知与覆盖：<未读到的模块、测试、运行证据>
```

缺失正式需求时可继续提供“代码可观察行为”背景，但必须标记为推断；不得声称需求已经验收。

## Gotchas / 易错点

- 部分暂存时工作区与候选代码不同：只以审查对象对应版本为准。
- 调用图可达不等于实际执行：条件、特性开关和动态分派需要二次核对。
- 测试名称不是需求事实：将其标为实现证据，并寻找正式验收依据。
- 缺少关键路径时先交付有限背景和待补证据，不用泛化“可能影响所有模块”。
